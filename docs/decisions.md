# 设计取舍与实测依据

这份配置中的参数设置并非默认推荐，而是对应具体的实测数据与边界约束。本文档汇总各项关键配置的决策结论、支撑依据以及对实际使用的影响，供二次调整时参考。

数字口径：token 计算一律按 chars/4 估算，或直接采用会话 JSONL 中的 `usage` 字段。**估算不能等同于实测**，两者的差异已在对应部分明确标注。

---

## 1. codemode only：首轮更精简，多步任务总开销更大

**决策**：在 `settings.json` 中配置 `{"codemode":{"mode":"only"}}`。配合 `pi-compact-tools` 插件时，直接向模型暴露的可见工具仅保留 `codemode`、`ask_user` 与 `tool_search`，其余 50 余个工具全部通过 QuickJS 沙箱脚本在运行时动态发现与调用。

**静态测量对比（两次探针，口径不同，请勿混用）**

| 探针条件 | 模型直接可见工具数 | 工具清单字符数 | 首轮 input token（含缓存读） |
| --- | --- | --- | --- |
| 探针 1：on → only | 39 → 4 | 3,471 → 432 | 26,704 → 16,261（约 -39%） |
| 探针 2：on → only + 优化系统提示 | 53 → 6 | 系统消息 35,464 → 23,913 字符 | 25,522 → 13,954（约 -45%） |

两次数字差异源于测试提示词与依赖版本的演进；当前版本实际仅保留 3 个直接工具。请勿将上述百分比直接等同于任意机器上的实际节省幅度。

**代价**：在 5 个典型对照任务中，only 模式下的输入 token 降低了 29%，但输出 token 增加了 36%（因为模型需要编写调用脚本）；而在多步调用任务中，总 token（input + cacheRead）约增加 **+17%**。即首轮提示词成本显著下降，但长链路多步调用的总体消耗有所上升。

**结论边界**：在探针 2 的对照实验中，两组测试同时变更了 `AGENTS.md` 与 `APPEND_SYSTEM.md`，因此效果差异无法单一归因于 codemode 机制；评测脚本主要依据关键词判定结果，且部分题目的答案可在文档中检索获得，因此**不能**据此推断 only 模式在任务准确率、错误率或误调用率上的绝对优劣。

**适用场景与权衡**：常驻工具 schema 属于每次网络请求均需附带的固定成本，only 模式将其压缩至极小；其主要代价在于模型需要编写 JavaScript 脚本驱动工具。该代价通过 `APPEND_SYSTEM.md` 中关于工具调用通道的约定以及参数错误恢复规则来弥补。如果你的核心使用场景以高频、多步骤工具交互为主，且对首轮提示词体积不敏感，使用默认的 `on` 模式同样是合理的选择。

**未采纳方案**：「核心工具常驻」（将 read/bash/edit/write 设为直接可见）。目前暂不引入该折中方案，建议在实际使用中先观察真实会话中的参数错误率、探测性调用占比与单工具脚本比例，出现明显瓶颈后再作调整。

## 2. 不设核心工具常驻，转而引入「参数错误恢复」规则

当工具从初始声明列表中移除后，模型的失败特征发生改变：模型不再直面完整的工具 schema，而是基于经验与记忆编写调用参数。实测中最普遍的错误是**参数结构偏差**（例如缺少必填的 `- path` 字段、或者将数字类型写为字符串），而非工具名称不存在。

因此，配置未选择重新暴露数十个常驻工具，而是在 `APPEND_SYSTEM.md` 中增加了一条明确的行为规范：

> 工具报参数错误时，先 `describeTool` 看声明，按报错修正参数后用**同一个**工具重试一次；不要换工具或换方法绕过去。

该方案的单次开销仅为一次额外的 `describeTool` 调用（几十 token），收益则是免除了每轮固定传输全部 schema 的负担。

配合另外两条规则——「不确定工具名称时先调用 `searchTools`」与「互不依赖的独立调用置于同一脚本中并行执行」，构成了轻量且具备自愈能力的「按需检索 + 快速纠错」调用闭环。

## 3. Magic Context 的三项核心阈值

| 参数 | 配置值 | 决策依据 |
| --- | --- | --- |
| `execute_threshold_tokens.default` | 400000 | 绝对触发阈值。插件默认策略为「上下文窗口的 65%」，在小窗口模型上容易过早触发压缩；400k 是基于公开发布的模型评测中 250k–500k 区间出现的注意力衰减特征、以及主流 harness 默认窗口所取的审慎值。当模型实际窗口低于 400k 时，Magic Context 会自动钳位在 90%。 |
| `memory.injection_budget_tokens` | 3000 | 注入预算限制。若设为 1000，60 余条已沉淀的项目记忆仅能注入 4 条，导致已有记忆无法有效发挥作用。 |
| `historian_timeout_ms` | 600000 | 压缩任务超时时间。会话总结归档属于重度推理任务。原默认 180000 ms 时超时率较高，且超时中断后模型后台仍在生成，导致同模型重试并重复产生费用。 |

**激进压缩策略的考量**：上下文并非越大越好。多项开源预填实验表明，部分模型在 250k 上下上下文时推理效果出现边际递减；部分平台对 1M 窗口模型的建议归档点也设置在 272k 至 500k 区间。这些公开数据表明了共同的方向：**基础提示词与常驻注入层务求精炼，具体细节依靠检索系统按需召回**。

**多配置同步注意**：如果同一环境中维护了多个启动入口（例如不同的 profile 配置文件），每个入口均会独立加载一份配置，各处的这三项参数必须保持严格一致，避免出现记忆读取行为不一致的隐蔽问题。

## 4. 搜索路由及回退顺序

配置规则：`searchRouting.providers: [exa, brave, bocha, gemini, degoog]`，触发降级条件：`fallbackOn: [empty, domain-miss, transient, quota, network, invalid-response]`。

**设计逻辑**：排序首位为结构化输出能力较强的通用搜索，其后配置具备正式 API Key 的商用搜索引擎，末尾由无需 Key 的搜索引擎提供兜底保底。将 `empty`（结果为空）与 `domain-miss`（域名未命中）同样纳入降级触发条件，是因为对实际交互而言，搜索无内容与网络超时带来的影响是相同的。

**运维与调整经验**：
- `searchRouting` 的规则调整需要**彻底重启 Pi 进程**才能完全生效（部分扩展在进程生命周期内缓存路由），仅执行 `/reload` 可能无法重载。
- 请勿将未配置可用凭据的 Provider 放置在首位。无可用 Key 时应直接从列表中移除该项，避免每次请求白白经历首轮失败延迟后再执行降级。

**网页正文抓取链路**：默认主路径为 `web_search → fetch_content`；当遭遇 403 或目标站点反爬阻断时，自动回退转入 Magpie 提供的 `web_fetch` 服务。需要注意：后者会对正文进行部分脱敏与掩码处理，正文中的特定地址、邮箱或哈希串可能被同形字符替换，**抓取获取的内容请勿直接作为凭据或配置原样使用**。

## 5. Magpie 外部网关的接管边界

**原则**：外部网关仅在能够有效减轻 Pi 的模型上下文开销或运维复杂度时接入，不追求无边界的代理间共享。

- **接管范围**：联网搜索（针对反爬的第二跳兜底）、图像与视频生成模型、技能索引优化（将第三方通用技能索引迁移至网关统一索引，实测使 Pi 的直接技能提示词从 11,276 字符精简至 6,545 字符，降幅 -42%）。
- **不予接管**：持久会话记忆、桌面/浏览器自动化。此类能力在本地已有更为成熟的原生实现，引入外部网关反而会造成双重状态维护混乱。

**集成注意事项**：
1. **请求头对 Hub 暴露工具的过滤**：网关在处理带有 `Sec-Fetch-Mode: cors` 请求头或浏览器 UA 的请求时，默认仅暴露基础搜索工具；而 Pi 底层基于 Node fetch 发出的调用天然携带此类请求头。因此图像生成等扩展能力必须通过独立的 stdio 进程启动（如 `magpie mcp image`），不能依赖 HTTP Hub 统一聚合。
2. **包含斜杠命令的交互技能保持独立注册**：如 `/skill:save-topic` 等需要用户在终端中明确执行斜杠命令的专属技能，一旦并入网关统一路由，Pi 将无法在本地注册同名命令，导致直接调用链路失效。因此，外部通用工具可委托网关瘦身，核心手动技能必须保留直接注册。

**独立性保证**：本套配置完全可以在脱离 Magpie 的状态下独立运行。只需将模型端点指向任意 OpenAI 兼容服务，`APPEND_SYSTEM.md` 中关于 Magpie 的引导规则已明确标注模块作用域，移除后不影响其它核心功能。

## 6. 分层记忆：RESIDENT 仅保留高价值事实

- **每轮固定注入**：仅注入 `RESIDENT.md` 文件内容（硬性上限为 6000 字符，日常实践中通常控制在数百至两千字符），专用于记录长期稳定、可被核验的个人偏好、环境特征与关键约束。
- **动态按需检索**：依靠本地知识库（pi-knowledge）存储项目技术历史、过往笔记与上下文片段，仅在匹配时检出。
- **后台自动归档**：长会话依靠 Magic Context 的 historian 模块自动执行阶段性压缩并生成项目事实摘要。

**注入实现方式的选择**：部分现成记忆插件通过「覆盖替换整个 `systemPrompt`」进行注入，这会直接破坏 Pi 插件间的链式调用契约，导致多个插件共存时相互覆盖。本配置扩展采用修改 `event.systemPromptOptions.sections` 的方式注入独立区域，不仅具备组合兼容性，且对 KV Cache 保持高度稳定。

**常驻记忆处理规范**：
1. 超长截断必须严格截断于行边界，杜绝半句残缺事实影响模型判断。
2. 仅当文件返回 `ENOENT` 时认定为无记忆；文件权限异常、编码错误或读取失败均需显式告警，避免由于配置错误导致记忆被静默忽略。
3. 注入数据仅作为背景上下文参考，不能授予系统执行权限，不得覆盖 `AGENTS.md` 设定的安全规则或用户的明确即时指令。

## 7. 界面精简：compact-tools

通过插件对终端工具输出进行折叠呈现（配置为 `previewLines: 8`，`edit` 修改保持默认展开，其他工具折叠输出），同时完整保留思考推理过程。原因在于：在 codemode 模式下，模型接收的有效返回由 JavaScript 脚本组织；在终端渲染数千行原始 diff 或构建日志既影响人工审阅，对上下文也无实质助益（折叠仅作用于前端展示层，不影响模型实际获取的内容）。保持 `edit` 工具展开则确保代码修改始终处于人工即时审查视野内。

## 8. 多子代理角色分工与模型搭配

- **执行角色（廉价高频）**：负责运行测试、脚手架搭建、前端界面及基础批量修改。选型标准为能够快速执行脚本、支持连续改动、允许失败重试。
- **复核角色（异构独立审阅）**：负责查阅 diff 变更、排查潜在逻辑漏洞。**建议选择与执行角色不同家族的模型**，降低同源训练带来的认知盲区。
- **规划角色（旗舰强力）**：负责系统架构设计、跨模块依赖评估、模糊需求澄清与疑难问题突破。

多模型搭配的核心目标在于借助模型差异分散同源盲区，其代价是需要配置并维护多套模型凭据与配置映射。各角色在具体环境中的对应模型由用户在部署阶段根据实际持有的 API Key 自行指定，角色之间的职责边界与设计定位保持不变。

## 9. 辅助配置项设计说明

- `defaultTools: ["+codemode","+grep","+find"]`：明确声明保留基础只读检索工具偏好；在启用 `pi-compact-tools` 时，grep 与 find 同样进入沙箱按需检索通道，保持顶层直接可见工具数收敛为 3。
- `retry.provider.timeoutMs: 3600000`、`maxRetries: 0`：Provider 底层关闭自动重试，将重试控制权完全交由上层调度；避免底层自动重试掩盖网络故障并在长链路执行中成倍累加等待时间。
- `compaction` / `branchSummary` 显式声明 `reserveTokens`：锁定上下文缩减时的保留量，避免因不同工具版本默认值波动导致基线不一致。
- `enableInstallTelemetry: false`：关闭安装时的遥测数据上报。
- `showCacheMissNotices: true`：开启缓存未命中通知，作为定位推理费用异常波动的直观观测信号。
