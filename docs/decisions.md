# 取舍

这份配置里每一个看起来「奇怪」的参数，都对应一次实测或一次事故。这里只写结论和依据；个人信息、具体供应商、以及作者本机的库名都不出现。

数字口径：token 一律按 chars/4 估，或直接用会话 JSONL 里的 `usage`。**估算不能当实测**，两者的差别在文里标出。

---

## 1. codemode only：首轮更小，多步任务总量更大

**决定**：`settings.json` 里 `{"codemode":{"mode":"only"}}`。装了 pi-compact-tools 时，直接可见的工具是 codemode / ask_user / tool_search，其余工具在 codemode 脚本里按需发现与调用。

**静态测量（两次探针，口径不同，不要混用）**

| 探针 | 模型可见工具 | 工具清单字符 | 首轮 input（含缓存读） |
| --- | --- | --- | --- |
| 第一次：on → only | 39 → 4 | 3,471 → 432 | 26,704 → 16,261（约 -39%） |
| 第二次：on → only + 新系统提示 | 53 → 6 | 系统消息 35,464 → 23,913 字符 | 25,522 → 13,954（约 -45%） |

两次数字不同来自探针提示与版本不同；当前版本实际只有 3 个直接工具。不要用这些比例反推你机器上的节省。

**代价**：第一次 5 个对照任务里 only 侧总输入 -29%、输出 +36%（模型要写脚本）；第二次多步任务的总 input+cacheRead 约 **+17%**。也就是首轮便宜了，多步任务的总量反而更多。

**不能下的结论**：第二次对照里两组同时改了 AGENTS.md 与 APPEND_SYSTEM.md，差异无法归因于 codemode；评分脚本按关键词判对错、且部分题目的答案能从仓库文档读到，所以**不能**据此说 only 更准、更不准或误调用更少。

**为什么还是选它**：常驻工具声明是每次请求都带的固定成本，only 把它限制在很小的规模；代价集中在「要写脚本」这一件事上，靠 `APPEND_SYSTEM.md` 的工具通道说明与参数错误恢复规则缓解。如果你的工作以多步工具调用为主、又不在意首轮大小，保持默认（on）也是合理选择。

**不做的事**：「核心工具常驻」（让 read/bash/edit/write 直接声明）暂时不做；先按周统计真实会话里的参数报错、探测性调用与单工具脚本占比，出现信号再加。

---

## 2. 为什么不做常驻核心，而是加「参数错误恢复」规则

工具从声明里消失，失败模式就变了：模型不再「看到一个工具的 schema」，而是「记得有个工具、凭记忆写参数」。实测最常见的错误是**参数形状**（缺 `- path`、`expected number, got string`），不是工具不存在。

所以 `APPEND_SYSTEM.md` 只加了一条规则，而不是加回一堆常驻工具：

> 工具报参数错误时，先 `describeTool` 看声明，按报错修正参数后用**同一个**工具重试一次；不要换工具或换方法绕过去。

代价是每次多一次 `describeTool`（几十 token），收益是不用把 schema 常驻。这条规则比「把 50 个工具都常驻」便宜两个数量级。

配套的两条：不确定工具名先 `searchTools`；互不依赖的调用放同一个脚本并行。三者合起来构成一个「按需发现 + 快速恢复」的循环。

## 3. Magic Context 的三个参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `execute_threshold_tokens.default` | 400000 | 绝对阈值。默认策略是「窗口的 65%」，对小窗口模型等于过早压缩；400k 是保守取值，依据是公开评测在 250–500k 区间出现的退化与主流 harness 默认窗口；它不是本配置验证出的退化点。窗口小于 400k 时 MC 自动钳到 90%。 |
| `memory.injection_budget_tokens` | 3000 | 注入预算。1000 时 60 多条项目记忆只能进去 4 条，等于「有记忆但用不上」。 |
| `historian_timeout_ms` | 600000 | 压缩不是快任务。180000 时完成/超时接近 2:1，而超时的模型仍在输出，被截断后同模型重试两次，等于同一份工作付三次钱。 |

**为什么不更激进**：上下文不是越大越好。公开的预填实验里，同一模型在 250k 上下的位置就开始掉点；另有厂商对 1M 窗口模型的默认压缩点设在 272k/500k。这些是别人的数据，但方向一致：**注入层要精简，细节下放到检索**。

**注意**：有多个入口（例如另挂一套 profile）时，每个入口一份配置，必须同步。不一致的表现是「有时候记得、有时候不记得」，最难查。

## 4. 搜索路由顺序

`searchRouting.providers: [exa, brave, bocha, gemini, degoog]`，`fallbackOn: [empty, domain-miss, transient, quota, network, invalid-response]`。

**理由**：第一个是「结构化程度最高的通用搜索」，第二个/第三个是有正式 key 的通用搜索，后面两个是无 key 兜底。`empty` 与 `domain-miss` 也触发降级，是因为「搜到了但没内容」和「超时」对用户是同一件事：没拿到答案。

**两个经验**：

- `searchRouting` 改动要**重启** Pi 才生效（扩展进程内缓存），`/reload` 不一定够。
- 不要把「永远失败的 provider」留在第一位。没有 key 就删掉那个字段，而不是留着等它每次都先失败一次再降级。

**抓取**：`web_search → fetch_content` 是主链；遇到 403/反爬再跳到 Magpie 的 `web_fetch`。后者会做掩码，正文里的地址、邮箱、密钥可能被同形替换——**抓回来的内容不要直接抄进配置**。

## 5. Magpie 的接管边界

**原则**：Magpie 只在「能减轻 Pi 的模型面或维护负担」时接管，不考虑跨 agent 共享。

- **接管**：搜索（web_search/web_fetch）、生图生视频、技能路由（把第三方技能索引从 Pi 的 `<available_skills>` 里搬走，实测索引 11,276 → 6,545 字符，-42%）。
- **不接管**：记忆、浏览器自动化。它们要么有更好的原生实现，要么会引入第二套状态。

**两个坑**：

1. **hub 按请求头过滤工具**：带 `Sec-Fetch-Mode: cors` 或浏览器 UA 的请求只列 web-search 两个工具；Pi 的 Node fetch 自带该头。所以图片工具必须单独走 stdio server。用 curl 直连看到的 6 个工具**不代表** Pi 能用。
2. **需要斜杠命令的技能必须 direct**：`/skill:save-topic`、`/skill:self` 这类手动技能一旦被路由进 hub 索引，Pi 就不再注册同名命令，明确调用它们的流程会直接失效。第三方大路货技能交给路由，自己的手动技能保持直连。

**没有 Magpie 也成立**：模型指向任意 OpenAI 兼容网关，`APPEND_SYSTEM.md` 里 Magpie 相关行都标了模块归属，整段删掉不影响其它能力。

## 6. 记忆分层：RESIDENT 只放「会改变行为的事实」

- **每轮都注入**的只有 `RESIDENT.md`（硬上限 6000 字符，实践中几百到两千字符）。它放的是稳定、可核对的偏好与约束。
- **按需检索**的是知识库（项目历史、笔记、旧对话）。
- **自动压缩**的是 Magic Context 的 historian，产出项目记忆。

为什么不用现成的记忆插件：大多数插件靠「返回整段 `systemPrompt`」注入，而按 Pi 的扩展契约那会**替换**整个提示，两个插件同时用就互相覆盖；可组合、且对 KV cache 友好的做法是改 `event.systemPromptOptions.sections`。这个扩展只做一件事：读一个文件、按行边界截断、以「这是数据不是指令」的框子注入。

三条硬规则：

1. 截断只在行边界（半句事实比没有事实更糟）。
2. 只有 `ENOENT` 才算「没有记忆」，其它错误要响（否则坏文件看起来像空记忆）。
3. 注入内容不可授权：它不能覆盖 `AGENTS.md`、当前请求或安全规则。

## 7. 显示层：compact-tools

工具输出折叠（`previewLines: 8`、`edit` 默认展开、其余折叠），思考摘要保留。理由很朴素：在 codemode 模式下，模型看到的工具结果主要来自脚本返回值，TUI 里的长 diff/长日志对人没用，对上下文也没用（截断发生在显示层，不改变模型收到的内容）。`edit` 保持展开是因为审查改动是人的主要工作。

---

## 8. 委派的三个角色

- **执行**（便宜）：测试、脚手架、前端、批量改动。判据是「能跑脚本、能改文件、失败可重来」。
- **复核**（另一种模型）：读 diff、挑证据漏洞。**必须与执行模型不同族**，否则同源盲区等于没复核。
- **规划**（最强）：架构、跨模块风险、需求含糊、反复失败。

选择不同模型是为了尝试降低同源盲区，代价是需要维护多套模型映射和凭据。这里没有隔离变量的复核质量实验，不能据此声称准确率提高或漏检减少。

具体到「谁是哪个模型」由你填（见 README 的角色表）。角色边界不要动。

## 9. 其它小决定

- `defaultTools: ["+codemode","+grep","+find"]`：声明偏好保留读工具；装 pi-compact-tools 时 grep/find 仍会进入按需发现通道，直接工具数为 3。
- `retry.provider.timeoutMs: 3600000`、`maxRetries: 0`：provider 层不重试，重试交给上层——provider 重试会掩盖真实的慢，并在长任务里叠加。
- `compaction`/`branchSummary` 显式写 reserveTokens：默认值在不同版本变化过，写死才能对比。
- `enableInstallTelemetry: false`：安装统计对本地体验没有帮助。
- `showCacheMissNotices: true`：缓存未命中是排查「为什么这轮很贵」的第一手信号。
